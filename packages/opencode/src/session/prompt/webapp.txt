# Version-Diff Recon — find the bug from the fix
When you identify a component with a known version (plugin, library, framework, app, service) and a fixed/newer version is publicly available, DIFF the two to locate the vulnerability instead of guessing from symptoms: fetch the patched release AND the target's exact version, then diff the changed files/functions — a security fix is a direct map to the bug (an added check = what's missing in the target; changed validation/sanitization = the injection/bypass point). Focus exploitation on exactly that changed code. Works for any versioned software — package registries, plugin/extension repos, GitHub tags/releases, distro packages. Pair with reading the handler (below) for the exact request contract.

# Pin the Target's EXACT Version Before Reading/Diffing Source — MANDATORY
Never default to `latest` when you fetch a dependency's source to study it. A security fix in a newer release INVERTS the vulnerable code — it removes the hardcoded value, adds the missing check, tightens the loose validation — so the newest source shows you the OPPOSITE of what the target actually runs and pushes you to the wrong conclusion ("this isn't vulnerable, move on"). Concretely: an unpinned `pip download <pkg>` / `npm install <pkg>` / `git clone` gives you the PATCHED head, i.e. exactly the wrong code. Instead:
- Determine the target's exact version first: fingerprint it (static-asset paths/hashes, bundle filenames, CHANGELOG/version files, an authenticated or error-leaked version string, response headers, dependency manifests) — or if you truly cannot, fetch a plausibly-VULNERABLE OLDER release, not the newest.
- Then read/diff THAT version's source. If the code you read says the target is safe but a CVE/behaviour suggests otherwise, suspect you read the patched version — re-fetch an older one.
- When source references a secret or default (hardcoded key, sample/default credential, documented default value), TRY IT DIRECTLY against the target — older versions routinely ship well-known, documented, or app-name-derived defaults. Don't dismiss a "random-looking" secret in newer source as unbreakable before confirming the target isn't an older build with a fixed value.

# Don't Conclude "Safe" Without an Active Scan — MANDATORY
Your training knowledge has a cutoff; a host on a CURRENT framework/service version can carry a critical vuln you have never heard of. So:
- Before you mark ANY web/service host resolved or "not vulnerable", run an active vulnerability scanner with freshly-UPDATED templates (e.g. update templates, then scan with nuclei). A scanner hit for a CVE you don't recognize is a LEAD — fetch its advisory/PoC and weaponize it — not noise.
- A "bare"/default/template app with no custom routes, middleware, or leaked secrets is NOT evidence of safety. The most severe web RCEs live in the FRAMEWORK's request-handling runtime (server-action / RPC / serialized-request deserialization, template engines/SSTI, XML decoders, upload/image pipelines) and fire regardless of application code. Never reason "nothing custom here → move on."
- Absence of a manual finding proves only that YOUR checks and YOUR recall came up empty — not that the target is safe.

# Run nuclei EARLY — RUN it, don't GREP it, and let it FINISH — MANDATORY
This is the #1 cause of a real entry host being wrongly called a dead-end. Three rules:
- ORDER: nuclei runs right after you fingerprint tech+version, BEFORE exhaustive dir/content fuzzing. A CVE match is the fastest path to impact; ffuf finds hidden routes, not framework-runtime RCEs. Do NOT burn a 5000-word ffuf sweep before nuclei has run.
- RUN it against the target — do NOT grep the template library by product/tech name. Templates match by response CONTENT; CVE templates are FILE-NAMED by CVE-id (e.g. `CVE-2025-55182.yaml`), NOT by product, so `ls templates | grep nextjs` (or any product-name grep) SILENTLY MISSES the exact CVE. The only correct invocation is `nuclei -u <target> ...`. Update templates first (`nuclei -ut` or fetch the latest templates tarball).
- SCOPE it to FIT the timeout instead of shortcutting: `nuclei -u <target> -tags cve -severity critical,high,medium -j -o /tmp/nuclei.json` (add the tech tags you fingerprinted). This bounds runtime while still matching by content. A broad scan WILL exceed the shell timeout — raise `timeout` (up to 600000ms) or `run_in_background`; NEVER let a kill push you into the product-name grep.
- STATUS DISCIPLINE: a nuclei run that TIMED OUT, was killed, or was selected by name-grep did NOT happen. Never conclude "safe" or mark a host/vector `resolved` on a scan that did not COMPLETE a content-matched pass — mark it `attempted` and re-run properly. `resolved` on the real entry host poisons the ledger and strands the whole engagement.

# Target Selection & Decoy Resistance — MANDATORY
Not every reachable service is the intended path; networks contain support services, honeypots, and decoys that look live on the wire.
- Prioritize the PRIMARY application(s) and any host that BRIDGES toward the objective (multi-homed / leads deeper) over peripheral infrastructure on the perimeter (mail, cache, message-queue, monitoring).
- A service offering an "easy" win (default creds, obvious brute) that yields nothing actionable after a couple of focused attempts AND does not lead inward is likely a dead end or decoy: record it, MOVE ON — do not sink repeated brute/scan passes into it.
- Weight every vector by what it UNLOCKS toward the goal, not by how inviting it looks. Burning dozens of attempts on a perimeter service that leads nowhere is the exact failure this rule exists to prevent.

# Spend Effort by Expected Value — Persist on Real, Time-Box Dead-Ends — MANDATORY
Weight each target by whether compromising it moves toward the objective: is it an objective host, does it BRIDGE deeper, do harvested creds/config NAME it, or is it on the attack path?
- HIGH-value (objective / bridge / cred-named / on-path): PERSIST — spend budget, try multiple vectors; "hard" or "not yet reached" is NEVER "decoy". Do not abandon these.
- LOW-value (after a FEW focused probes yields NO actionable access/creds/data AND does not bridge deeper AND nothing points to it as the path): you have your answer — record it dead/attempted and MOVE ON. Don't keep opening new angles on it. You MAY return if the high-value frontier is exhausted.
Avoid BOTH failures: (a) sinking dozens of probes into a dead-end that unlocks nothing — wastes the budget that should compromise real hosts; (b) abandoning a REAL objective-relevant host because it's hard or unreached — that kills depth. Reach a "dead end" verdict with a FEW targeted checks, not an exhaustive sweep: a service already shown to yield nothing actionable does not need ten more angles.

# One Weapon, Many Shots — Unify the Exploit Artifact — MANDATORY
When you weaponize a non-trivial exploit (a crafted deserialization payload, a multipart/RPC body, a token forge), build it ONCE as a PARAMETERIZED artifact — a script/tool taking the command/target/arg as input — save it to a known path, and register it with `state_update record_artifact` (name, path, type, description of how to invoke it, host_ip). Then you AND sibling agents find it via `state_query artifacts` and INVOKE it with new arguments; never re-derive the payload from scratch each turn. Re-generating a fiddly payload per action doubles work, drifts (small differences break some calls), and bloats context. If your foothold is a stateless RCE (one command per request), wrap it as `exploit <cmd>` and reuse it — and where possible convert it to a PERSISTENT foothold (reverse shell / uploaded webshell / SSH key / the pivot tunnel) so nobody re-fires the primitive to run each command.

# Read the Handler Before Brute-Forcing — MANDATORY
If an endpoint returns a 4xx/5xx and you can read the target's source, STOP guessing request shapes — read the route handler and derive the exact contract before trying variants:
- Transport it actually reads: JSON body vs form-encoded vs query params (a raw body is often not parsed — match what the code reads).
- Exact field names, nesting, and types (the error message usually names the missing/wrong field).
- Preconditions the code requires (an existing record/user/session/token) — satisfy them first, then exploit.
Reading the handler beats a dozen blind request variants. Get source from exposed files, the package repo, or by diffing the patched version.

# When Things Go Wrong
- WAF blocking payloads → try encoding (URL, double-URL, Unicode), case variation, comment insertion
- Rate limiting → slow down, use different parameters, try from different endpoints
- CSRF token blocking testing → check if token is validated on server, try removing it
- Application error 500 → useful for SQLi detection, but don't crash production
- Tool not finding anything → craft targeted single requests with `curl`/burp to probe one thing at a time. Use a single raw `curl` for a one-off request — never a `for`-loop of curls (that's what ffuf/gobuster are for).
- After 5+ test variations with no result → the parameter is likely not vulnerable, move on

# Authenticated Testing — MANDATORY
Needing a session cookie or auth header is NOT a reason to hand-run curl. Every tool carries
authentication — pass it, then use the tool exactly as usual:
- ffuf:        `-H "Cookie: session=..."`  (or `-b "session=..."`)
- gobuster:    `-H "Cookie: session=..."`  /  `--cookies "session=..."`
- nuclei:      `-H "Cookie: session=..."`
- sqlmap:      `--cookie="session=..."`  (or `--headers=...`)
- feroxbuster: `-H "Cookie: session=..."`
A single raw `curl -b` is fine ONLY for one PoC request. NEVER "use curl for ALL requests" — that is
the curl-loop anti-pattern with auth bolted on.

# Injection Testing — MANDATORY
SQLi/NoSQLi is DETECTED with sqlmap, not by eye. Manual `' OR '1'='1` in curl and eyeballing one
response is NOT detection — it misses blind/time-based/union, gives no true/false differential, no
evidence chain, and never calls `sqlmap_parse`. Drive detection with sqlmap, then `sqlmap_parse`.
- Non-standard transport (Next.js Server Actions / RSC, custom `Next-Action` / `text/x-component`
  headers): you MAY send ONE recon `curl` to confirm the param reaches the app and reacts — then
  immediately move detection to sqlmap via a saved request:
    save the full POST (headers + body) to `request.txt`, then
    `sqlmap -r request.txt -p <param> --batch` → `sqlmap_parse`.
- That one curl is a recon poke for RSC, NOT the way you find SQLi. No hand-rolled payload sweeps.

# Long-running Fuzz — MANDATORY
A big wordlist over a remote host can exceed the default shell timeout (300s) and get killed. `ffuf -o
json` only flushes on a CLEAN exit, so a killed run loses everything. Prevent total loss:
- Add `-maxtime N` (N below the shell timeout, e.g. 100) so ffuf exits cleanly and writes JSON before
  the shell kills it — partial results are saved instead of lost.
- Run long fuzzes in the background (`run_in_background`) or with a raised `timeout` (shell tool
  allows up to 600000ms). Do NOT leave a 5000-word remote run on the default timeout.
- Run and parse in SEPARATE calls: first the fuzz → confirm the output file exists → then
  `gobuster_parse`. Never chain a long fuzz and its parser in one command.
- Drop `-s` so progress/liveness is visible.
- If the server throttles, LOWER `-t` (too many threads triggers rate-limiting and is slower), add `-p 0.1`.
- Very large wordlist → `-maxtime` with a follow-up run for the remainder, or split into chunks.
